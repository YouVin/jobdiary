# 📋 익스텐션 기획

현재 공통 계약과 지원 이력 비교 캐시는 [5단계 구현 기록](../../../docs/APPLICATION_HISTORY_SYNC.md)을 따른다.
실제 채용 페이지 자동 표시는 다음 단계이며 아래 초기 기획과 구현 상태를 구분한다.

## 프로젝트: 취준일기 익스텐션

---

## 1. 목적

취준일기 웹앱의 핵심 가치("입력이 아니라 수집")를 실현하는 도구. 유저가 직접 타이핑하지 않고, 지원현황 페이지에서 버튼 한 번으로 지원 내역을 수집한다.

## 2. 왜 익스텐션인가

- 사람인/원티드/잡코리아는 **개인 지원내역 공개 API가 없음**
- 크롤링(서버에서 로그인)은 약관 위반 + 보안 위험
- 익스텐션은 **유저 브라우저에 이미 로그인된 화면**을 읽으므로 안전하고 합법적
- 실제 검증: 잡코리아 나인하이어도 동일한 "클릭 한 번 수집" 방식 사용

## 3. 검증 완료 사항

3개 사이트 HTML을 직접 분석해 **모두 수집 가능함을 확인**:
- 사람인: data 속성으로 회사명/공고명 직접 제공
- 잡코리아: data 속성 + 명확한 class
- 원티드: class 부분매칭으로 수집 가능

상세: [SELECTORS.md](./SELECTORS.md)

## 4. 핵심 기능 (MVP)

| 기능 | 설명 | 우선순위 |
|------|------|---------|
| 지원현황 페이지 감지 | 3개 사이트 지원현황 URL에서 동작 | 🔴 필수 |
| "가져오기" 버튼 삽입 | 페이지에 수집 버튼 표시 | 🔴 필수 |
| 지원 목록 파싱 | 회사/공고/상태/지원일 추출 | 🔴 필수 |
| 상태 매핑 | 사이트 원문 → 취준일기 Status | 🔴 필수 |
| 사이트별 누적 저장 | chrome.storage.local에 사이트별 슬롯으로 저장, 재수집 시 해당 슬롯만 덮어씀. 중복 판별(platform+externalId 등)은 익스텐션이 하지 않고 웹앱 addApplicationsFromExtension이 전담 (상세: [INTEGRATION.md](./INTEGRATION.md)) | 🟡 중간 |
| 웹앱 전달 | 수집 데이터를 취준일기로 | 🔴 필수 |
| popup UI | 아이콘 클릭 시 요약/이동 | 🟡 중간 |

## 5. 개발 순서

```
1. 프로젝트 세팅 (CRXJS + Vite)
2. 사람인 파싱 (제일 쉬움) → 콘솔에 데이터 찍어 검증
3. "가져오기" 버튼 삽입 + 파싱 연결
4. chrome.storage 저장
5. 누적 저장 + 전체 복사 (chrome.storage.local에 사이트별 슬롯 저장, 3사이트 합쳐 TSV+HTML 복사)
6. 웹앱 전달 방식 구현
7. 잡코리아 확장
8. 원티드 확장
9. popup UI
10. 크롬 웹스토어 배포
```

**원칙: 사람인 1개를 끝까지 완성(파싱→저장→전달)한 뒤 나머지 복제.**

## 6. 웹앱 연동 방식

익스텐션이 파싱 결과를 변환해 chrome.storage에 저장하고, 팝업에서 웹앱을 열면
웹앱이 `JOBDIARY_COLLECT`로 저장 결과를 요청한다. 웹앱이 자신의 로그인 세션으로
저장하며 익스텐션은 인증 토큰이나 웹앱 DB를 직접 다루지 않는다.
(현재 구현과 응답 형식: [INTEGRATION.md](./INTEGRATION.md))

## 7. 데이터 정합성 / 저장 전략

- **저장 구조**: chrome.storage.local에 사이트별 슬롯(`{ saramin, jobkorea, wanted }`)으로 누적 저장한다. 같은 사이트를 다시 수집하면 그 슬롯만 최신 결과로 덮어쓴다 — 사이트 단위 스냅샷이며 병합이 아니다.
- **데이터 유지**: 클립보드로 복사해도 저장된 데이터는 자동으로 비우지 않는다. 유저가 "초기화" 버튼을 눌렀을 때만 전체 슬롯을 비운다.
- **전체 복사**: 3사이트 슬롯을 합쳐 TSV + HTML 표로 클립보드에 넣는다. 사이트별 수집 시 쓰는 복사 로직(E-6)을 그대로 재사용한다.
- **중복 방지(웹앱 전담)**: 익스텐션은 사이트별 덮어쓰기로만 관리한다. 웹앱은 platform + externalId 우선, 없으면 정규화한 platform + company + position으로 기존 지원을 찾으며 기존 행은 수정하지 않는다. 최종 기준은 웹앱 수신 계약이다 (상세: [INTEGRATION.md](./INTEGRATION.md)).
- **익스텐션 저장**: chrome.storage.local을 사용한다. 웹앱은 자기 로그인 세션으로 저장하며 익스텐션에 별도의 백엔드 연결을 추가하지 않는다.
- **상태 매핑 실패**: applied로 기본 처리, 유저가 웹앱에서 수정
- **파싱 실패 대비**: 수동 저장 버튼 항상 제공

## 8. 리스크 & 대응

| 리스크 | 대응 |
|--------|------|
| 사이트 HTML 개편으로 셀렉터 깨짐 | 셀렉터 상수 분리, SELECTORS.md 관리, 수동 저장 백업 |
| 원티드 해시 class 변경 | 부분매칭(`[class*="..."]`) 사용 |
| 웹스토어 심사 | 권한 최소화, 개인정보 정책 명확화 (로그인 정보 미수집 명시) |
| 로그인 안 된 상태 | 안내 메시지 표시 |

## 9. 제외 범위 (MVP 아님)

- 자동 백그라운드 수집 (유저가 버튼 눌러야 함 — 의도적)
- 자동 지원 (약관 위험)
- 지원현황과 무관한 페이지 수집 (마감일 보충은 해당 지원과 연결된 잡코리아 공개 공고 상세의 메타 정보만 허용)

## 10. 선택적 마감일 작업 (#60 / #63)

- #63: 선택적 원문/전달 타입, 엄격한 날짜 검증, 어댑터·저장·외부 응답 경로 테스트 준비
- #60: 사람인 모바일 한 페이지의 명시 날짜를 PC 지원에 보충하는 경로 구현. 실제 로그인 요청·페이지네이션·실사용 확인 필요
- 잡코리아는 마감 표시와 연결된 공개 공고의 메타 날짜/JSON-LD 날짜/공고 ID를 교차 검증해 보충한다. 상시와 미확인은 생략한다. 원티드는 출처가 없어 생략한다. 사람인은 지원 ID+공고 ID가 일치하는 모바일 제목의 전체 날짜만 보충한다.
- 마감일은 확인된 날짜만 웹앱에 전달하며 자동 상태 변경은 웹앱의 책임이다.
- 기존 웹앱 지원의 마감일은 재수집으로 갱신하지 않는다.
- 마감 표시를 읽는 동작을 개인정보처리방침·권한 설명에 반영했다. 실제 날짜 전달을 출시할 때 스토어 설명과 정책의 일치를 재확인한다.
- 세부 진행 상태: [DEADLINES.md](./DEADLINES.md)
