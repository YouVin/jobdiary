# 공고 마감일과 자동 탈락 분류

현재 구현 기준: 2026-10-15 (#85).

지원 내역의 `deadlineAt`은 선택적인 `YYYY-MM-DD` 날짜다. 추가·수정 화면에서 직접 입력하며, 빈 값은 상시채용 또는 마감일 미확인으로 취급한다. 익스텐션 응답에도 선택적으로 허용하지만, 현재 익스텐션이 사이트에서 마감일을 수집하는 기능은 [별도 이슈](https://github.com/YouVin/jobdiary-extension/issues/60)다. 익스텐션 원본에는 `viewed`가 있지만 현재 웹앱의 저장 계약에는 열람 여부가 없어 이번 규칙에 사용하지 않는다. 기존 지원을 다시 수집해도 마감일을 포함한 기존 행은 갱신하지 않는다.

한국 날짜 기준으로 **마감 다음 날** 대시보드를 열었을 때도 상태가 `지원완료`이고 사용자가 상태를 직접 옮긴 적 없는 건만 `탈락`으로 바꾼다. 익스텐션에서 추가된 건(`extension`)과 새로 직접 추가한 건(`created`)이 대상이다. 사용자가 상태를 옮겼다면 다시 `지원완료`로 되돌렸어도(`manual`) 자동 분류하지 않는다. 마감 당일, 마감일 없음, 서류·면접 등 진행 중인 건과 이미 종료된 건도 변경하지 않는다. 과거 마감일을 새로 저장하는 경우도 같은 규칙을 적용한다. 여러 탭에서 동시에 열어도 DB의 현재 상태·출처·마감일 조건을 만족하는 행만 갱신한다. 자동 분류된 행은 `statusSource='deadline'`으로 구분하고 카드에 근거를 표시한다. 실제 기업의 불합격 통보를 확인한 결과가 아니며, 이번 웹앱 규칙은 열람 여부를 판단하지 않는다.

자동 분류는 대시보드 조회 시점과 대시보드를 열어 둔 채 한국 날짜가 바뀐 뒤 다시 활성화될 때 실행한다. 열린 탭은 1분 간격으로 날짜 변화를 확인한다. 페이지를 열지 않는 동안 서버 백그라운드 작업은 돌지 않는다. `지원완료`로 유지하고 싶으면 분류 전에 마감일을 비우거나 수정해야 한다. 이미 자동 분류됐다면 상태와 마감일을 함께 수정할 수 있다.

기존에 직접 추가한 지원은 과거 구현에서 추가와 상태 변경을 모두 `manual`로 기록했으므로 두 경우를 구분할 수 없다. 이 기존 데이터는 사용자 선택을 보호하기 위해 자동 분류에서 제외한다. 이 기능 배포 후 직접 추가한 지원부터 `created`로 기록한다.

배포 순서: [`deadline_at` 및 상태 출처 마이그레이션](../supabase/migrations/20261016124556_application_deadline_auto_rejection.sql)을 대상 Supabase 프로젝트에 적용한 다음 웹앱을 배포한다. 운영 프로젝트에는 이미 적용됐다. #96에서 원격 이력의 실제 버전으로 복원했으며 이전 파일 `20261015102447`은 중복 실행을 막기 위해 제거했다. 저장소에 파일이 있다고 DB에 자동 적용되는 것은 아니다.

편집창 저장 충돌 보호 (#93): 폼을 열 때의 상태·출처·`updatedAt`을 기준으로 편집한다. 저장은 DB에서 `id`, 본인 `user_id`, 기준 `updated_at`이 모두 일치할 때만 수행한다. 다른 탭이나 대시보드 새로고침으로 내용이 바뀌었거나 행이 삭제됐다면 오래된 입력으로 덮어쓰지 않고 수정창에 페이지 새로고침을 안내한다. 편집 도중 최신 props가 들어와도 기준 버전은 바꾸지 않는다. 드래그는 사용자의 명시적인 상태 이동이므로 기존 방식으로 처리한다.

날짜 입력 검증 (#94): 추가·수정 화면은 지원일을 필수 `YYYY-MM-DD` 날짜로 검증한다. 마감일과 면접일은 비울 수 있고, 입력한 경우에는 실제 존재하는 날짜인지 확인한다. 잘못된 날짜는 ISO 변환이나 저장 요청 전에 오류 문구로 안내하고 폼을 유지한다. 수정 시 선택 날짜를 비우면 `null`로 전달해 DB에서도 비운다. 입력 규칙은 `src/utils/applicationFormValidation.ts`에서 공유한다.
