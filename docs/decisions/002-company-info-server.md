# 002. 회사 정보 서버를 Supabase Edge Function에 두기

| 항목 | 내용 |
|---|---|
| 상태 | **결정** (구현 #228, 화면 #229) |
| 날짜 | 제안·결정 2026-11-24 |
| 관련 이슈·PR | #228, #229 |
| 결정한 사람 | 개발자 |

## 1. 문제

- 지원 상세의 "회사 정보"(공고 인재상 → 강점, 기술, 회사 한 줄 소개)를 만들려면 AI(Claude)를 불러야 한다.
- AI 키는 브라우저에 둘 수 없다. 그런데 웹앱에는 서버 API가 하나도 없고, 브라우저가 Supabase를 직접 부른다.
- 같은 공고 결과를 사용자끼리 같이 쓰고(비용 절약), 하루 사용 횟수를 막으려면 브라우저가 고칠 수 없는 곳(서버 권한)에서 저장해야 한다.

## 2. 지금 숫자

| 지표 | 값 | 잰 방법 |
|---|---|---|
| 서버 API | 0개 (`apps/web/src/app`에 route 없음) | 폴더 확인 |
| Edge Function | 1개 (`delete-account`, verify_jwt) | `supabase/functions` |
| 분석 1건 비용 | 약 $0.0007 (1원), 4.6초 | 결정 기록 001 6절 (가상 공고 1개, Haiku 5.5 lean) |

## 3. 선택지

| | A. Next.js 서버 API (Vercel) | B. Supabase Edge Function |
|---|---|---|
| 요약 | `apps/web/src/app/api/...` route | `supabase/functions/company-info` |
| 장점 | 측정한 지시문 코드를 그대로 import. 배포가 지금과 같다 | **서버 역할을 Supabase 한곳에 모은다.** 계정 삭제라는 선례가 있다. service_role이 Supabase 안에만 있다 |
| 단점 | 결과 공유·한도 저장에 service_role 키를 Vercel에도 둬야 한다(키가 두 곳) | 지시문 코드를 Deno가 읽을 수 있는 곳으로 옮겨야 한다. 함수 배포가 따로 있다 |

## 4. 결정

**AI 추천:** A. 측정한 코드를 그대로 써서 "잰 것 = 서비스하는 것"을 지키기 쉽다.

**내 결정:** B. Supabase를 이미 서버로 쓰고 있으니 서버 코드를 한곳에 모으는 게 좋다.
- A의 장점(같은 코드 사용)은 지시문 코드를 `supabase/functions/_shared/`로 옮겨 Edge Function과 측정 스크립트가 같은 파일을 읽게 해서 지킨다.
- service_role 키가 Vercel로 퍼지지 않는다.

함께 정한 것:
- 이름: 화면 구역 이름은 "면접 준비"가 아니라 **"회사 정보"**.
- 하루 한도: 사용자당 하루(한국 날짜) **5번**. 하루에 5곳 넘게 서류 합격할 일은 드물다. 같은 공고 결과를 다시 쓰는 경우와 AI 실패는 세지 않는다.
- 범위: **1단계(서버) + 2단계(상세 패널 + 공고 붙여넣기)**까지 먼저 만들고, 써 보고 좋으면 3단계(서류 통과 시 자동 생성)로 간다.

## 5. 성공 기준과 검증 방법

- 처리 순서 단위 테스트: 로그인·본인 지원·한도·재사용·실패 시 한도 되돌림·지어낸 인용 제거 (Node, 가짜 DB·AI)
- SQL: 로컬 Postgres(PGlite)에서 마이그레이션 실행, 한도 6번 시도 → 5번만 성공, 사용자는 본인 회사 정보만 읽기, 캐시·한도 표·함수는 브라우저 역할로 접근 불가
- Edge Function Deno 타입 검사 통과
- 운영 반영 후: 실제 공고로 1건 만들기 → 같은 공고 다시 → 한도 안 씀, 6번째 새 공고 → 하루 5번 안내
