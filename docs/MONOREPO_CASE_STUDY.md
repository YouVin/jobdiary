# 웹앱·Chrome 익스텐션 모노레포 전환 사례

기록일: 2026-11-04 (한국 시간).
전환 이슈 [#111](https://github.com/YouVin/jobdiary/issues/111),
통합 PR [#112](https://github.com/YouVin/jobdiary/pull/112),
후속 검증 이슈 [#113](https://github.com/YouVin/jobdiary/issues/113).

이 문서는 포트폴리오의 근거 자료다. 운영 절차는 [이전 기록](MONOREPO_MIGRATION.md),
남은 외부 작업은 [전환 체크리스트](MONOREPO_HANDOFF.md)를 기준으로 한다.
아래는 모노레포 전환 시점(PR #112)의 확인 기록이며 이후 배포 상태를 보장하지 않는다.
후속 5단계에서는 실제로 공통 패키지와 지원 이력 동기화를 추가했다([구현 기록](APPLICATION_HISTORY_SYNC.md)).

## 해결하려던 문제

취준일기는 채용 사이트의 지원 내역을 수집하는 Chrome 익스텐션과, 이를 저장·관리하는
Next.js 웹앱으로 구성되어 있었다. 두 저장소가 각각 존재해 메시지 형식과 선택 필드,
가져오기 동작을 변경할 때 양쪽 구현·문서·검증을 따로 확인해야 했다.

다음 기능으로 지원 이력 자동 표시를 검토하면서 이 경계가 더 중요해졌다.
익스텐션의 수집 슬롯은 재수집할 때 교체되는 스냅샷이므로 장기 지원 이력의 기준으로
사용하기 어렵다. 웹앱에 저장한 이력을 바탕으로 비교용 정보를 익스텐션에 보내려면
양쪽의 데이터 계약·공고 식별·계정 전환 처리를 함께 변경하고 검증해야 한다.

이번 전환의 목표는 이 후속 작업을 한 저장소의 변경으로 검토할 기반을 만드는 것이었다.
지원 이력 동기화나 자동 표시를 이번에 구현한 것은 아니다.

## 선택한 구조와 대안

| 선택지 | 검토 내용 | 결정 |
| --- | --- | --- |
| 별도 저장소 유지 | 앱별 독립성은 유지되지만 계약 변경과 검증 기록을 두 곳에서 맞춰야 함 | 기존 운영 형태로 비교 |
| 기존 웹앱 저장소에 통합 | 대표 GitHub 주소와 Vercel 저장소 연결을 유지하면서 두 앱을 함께 관리 가능 | 채택 |
| 새 저장소 생성 | 이력·대표 링크·Vercel 연결을 함께 이전할 추가 작업 발생 | 이번 범위에서 선택하지 않음 |
| npm workspaces | 두 앱 모두 npm·TypeScript 사용. 루트 설치·잠금 파일과 앱별 명령 구성 가능 | 채택 |
| 별도 빌드 오케스트레이터 도입 | 현재 앱 2개와 독립 빌드에는 필수 요구가 확인되지 않음 | 도입 보류 |
| 공통 패키지 즉시 추출 | 공통 타입의 이름이 같아도 수집 데이터와 웹앱 저장 계약은 완전히 같지 않음 | 실제 계약을 확인하는 5단계로 분리 |

```text
jobdiary/
  apps/web/         Next.js 웹앱
  apps/extension/   Vite·CRXJS Chrome 익스텐션
  docs/             웹앱 및 통합 의사결정·검증 기록
  supabase/         기존 위치 보존
  package.json
  package-lock.json
  vercel.json
```

루트에서 한 번 설치하되 웹앱·익스텐션의 개발 서버, 빌드, 테스트, 버전·출시는 각각
운영한다. 동일 저장소에 있다고 브라우저 실행 환경이나 인증 상태가 합쳐지지는 않는다.
공통 패키지는 아직 없으며 폴더만 미리 생성하지 않았다.

## 단계별 진행과 보존 기준

1. 원격 main/dev, 로컬 미커밋·미추적 작업, 기존 배포 상태와 문서를 조사했다.
2. 원본을 변경하기 전에 Git bundle, 소스 ZIP, 패치와 파일별 해시를 보존했다.
3. 별도 복제본에서 두 앱의 테스트·빌드를 실행해 이전 전 기준을 확보했다.
4. 웹앱 기존 main/dev 이력을 연결하고 익스텐션 이력을 별도 부모로 연결했다.
5. 파일 이동과 workspace·경로 설정을 적용하고 실제 개발 폴더에서도 다시 검증했다.
6. 주소·익스텐션 ID·origin·환경 설정과 공개 Pages 의존성을 점검했다.
7. 기존 익스텐션 dev와 통합 저장소 dev에 각각 PR을 병합했다.
8. 병합 후 CI와 Vercel Preview 결과를 확인한 뒤 실제 로그인 검증을 별도 단계로 남겼다.

백업에는 미커밋 마감일 작업도 포함한다. 비밀값·개인키·사용자 설정·의존성과 빌드 산출물은
Git에 추가하지 않았다. 로컬 복구 자료의 위치와 범위는
[BASELINE_2026-11-04.md](BASELINE_2026-11-04.md)에 기록했다.

## Git 이력과 릴리스 태그 보존

단순 파일 복사와 하나의 초기 커밋으로 합치면 익스텐션의 과거 작업이 통합 저장소의
조상 관계에서 끊어진다. 따라서 기존 커밋을 squash하지 않고 merge 부모로 연결했다.
경로 이동은 별도 커밋으로 남겨 이전 작업과 기능 변경을 구분했다.

| 커밋 | 역할 |
| --- | --- |
| `d335faf` | 웹앱 dev 이전 기준 |
| `b0c87dc` | 웹앱 기존 main 배포 이력 |
| `08d5e46` | 웹앱 main 이력 병합 |
| `430b55d` | 익스텐션 기존 main 기준 |
| `0b09ed5` | 익스텐션 이력을 보존한 subtree 통합 |
| `debb2df` | 당시 미커밋 마감일 작업을 모노레포에서 분리 보존 |
| `8e2e6e9` | workspace·경로·CI 등 구조 변경 |
| `266813c` | 기존 익스텐션 저장소에 마감일 작업 커밋 |
| `5d81d3c` | 기존 익스텐션 PR #64의 dev 병합 |
| `3e67bfe`, `c8dd18d` | 익스텐션 최신 작업·최종 dev의 이력을 모노레포에 연결 |
| `977a9dc` | Vercel 출력 경로·Node 범위 수정 |
| `f3db5f9` | 모노레포 PR #112의 dev 병합 |

기존 익스텐션의 후속 이력을 연결할 때는 이미 옮긴 src 트리가 동일한지 확인한 뒤
`ours` merge 전략을 사용했다. 이력은 연결하되 이전의 평평한 폴더 구조를 다시
유입하지 않기 위한 선택이다. 충돌 해결 수단으로 무조건 사용하는 전략으로 일반화하지 않는다.

익스텐션 태그는 `extension/v1.0.0`부터 `extension/v1.0.3`까지 이름을 구분해
통합 원격에 보존했다. 향후 웹앱 태그와 같은 이름을 사용하는 문제를 피할 수 있다.
원본 이슈·릴리스 링크는 기존 저장소의 실제 이력을 가리키므로 유지했다.

아래 명령으로 보존 관계를 다시 점검할 수 있다. Windows Git 소유권 예외가 필요한
환경에서는 해당 명령에만 `-c safe.directory=C:/jobdiary`를 지정한다.

```sh
git merge-base --is-ancestor b0c87dc dev
git merge-base --is-ancestor d335faf dev
git merge-base --is-ancestor 430b55d dev
git merge-base --is-ancestor 5d81d3c dev
git tag --list "extension/*"
```

## 의존성과 경로에서 해결한 문제

두 앱의 잠금 버전·레지스트리 위치·무결성 값을 기준으로 루트 잠금 파일을 구성했다.
앱별 잠금 파일을 제거하고 `npm ci`를 루트에서 실행하도록 통일했다.
새 레지스트리 버전이나 직접 의존성 버전 변경이 함께 유입되지 않았는지 확인했다.
마이그레이션에 라이브러리 업그레이드까지 섞지 않아 실패 원인을 구분할 수 있었다.

의존성 hoisting으로 로컬 폰트 경로가 달라졌다. 실제 첫 빌드에서
`next/font/local`이 기존 앱 내부 node_modules의 Pretendard 파일을 찾지 못했다.
`apps/web/src/app/layout.tsx`의 정적 상대경로를 루트 node_modules 기준으로 수정했다.
폰트 파일과 표시 설정은 유지했다.

Next.js의 `turbopack.root`와 `outputFileTracingRoot`도 저장소 루트로 지정했다.
이로써 앱 위에 설치된 의존성을 빌드에서 다룰 기준을 명시했다.
변경한 경로와 이유는 설정 파일에 남기고 웹앱 소스의 다른 동작은 유지했다.

## Vercel Preview 실패와 수정

첫 자동 Preview에서는 빌드 후 Vercel이 저장소 루트의 `.next`를 찾으며 실패했다.
실제 Next.js 산출물은 이동한 앱 아래 `apps/web/.next`에 있었다.
열린 Node 범위 `>=22.12.0` 때문에 당시 Preview에서 Node 26을 선택한 사실도 로그로 확인했다.

프로젝트 대시보드의 공통 Root Directory를 즉시 변경하면 아직 이전 구조인 운영 main에도
영향을 줄 수 있다. 대신 모노레포 브랜치의 루트 `vercel.json`에 다음을 지정했다.

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "nextjs",
  "installCommand": "npm ci",
  "buildCommand": "npm run build:web",
  "outputDirectory": "apps/web/.next"
}
```

Node 범위는 `>=22.12.0 <25`로 제한했다. 로컬·GitHub Actions에서는 Node 22,
Vercel에서는 기존 프로젝트의 Node 24 계열로 검증했다.
루트 전체 빌드 대신 웹앱만 빌드하므로 Vercel 배포에 익스텐션 ZIP 생성이 필요하지 않다.

수정 후 최종 PR Preview와 병합된 dev Preview가 모두 READY가 되었다.
Root Directory는 저장소 루트로 유지할 수 있어, 현재 전환에 대시보드 경로 변경은 필요하지 않다.
main이 모노레포로 전환되면 소스의 동일 설정을 따라간다. 운영 반영은 아직 별도 작업이다.

## 통합에서 유지한 연결

웹앱과 익스텐션의 통신 대상은 GitHub 저장소 주소가 아니라 웹앱 origin과 익스텐션 ID다.
대표 저장소를 합쳤다는 이유로 통신 주소·스토어 항목을 새로 만들 필요는 없었다.
실행 코드와 생성 manifest를 확인하고, 공개 페이지의 HTTP 응답도 별도로 점검했다.

| 연결 | 결과 |
| --- | --- |
| 서비스 | `https://jobdiary.vercel.app` 유지 |
| Chrome 스토어 ID | `afnboeihbppogfinbickjaaadcgjkmil` 유지 |
| 개발 ID | `dckfpbmglbagcpnkkkdcnbnpjdpfjcde`, 공개키로 계산해 대조 |
| 익스텐션 권한 | 기존 storage·host 범위 유지 |
| 외부 메시지 | 운영 origin 및 개발용 localhost, 임의 Preview origin은 허용하지 않음 |
| Pages 안내·정책 | 기존 `youvin.github.io/jobdiary-extension/`와 `/privacy/` 유지 |
| 환경·인프라 | 기존 환경 파일 보존, Supabase 파일 변경 없음 |

실제 연결 지점과 추후 주의사항은 [주소·연동 점검](MONOREPO_LINK_AUDIT.md)을 따른다.
기존 저장소는 Pages·정책·이슈 링크의 의존성이 있어 유지한다.

## 확인된 결과와 아직 측정하지 않은 효과

확인한 성과는 두 앱의 소스·과거 이력·검증을 하나의 저장소에서 다루고,
앱별 빌드와 원래 서비스 연결을 유지한 채 dev 통합과 Preview를 완료했다는 것이다.
이후 양쪽 계약 변경을 한 PR에 담을 수 있는 구조를 확보했다.

개발 시간 감소율, 사용자 메모리 감소, 빌드 속도 향상이나 장애율 감소는 측정하지 않았다.
전환으로 모든 중복 코드가 없어졌다고 설명하지 않는다.
현재 CI는 각 job에서 전체 workspace 의존성을 설치하므로 설치 비용이 남아 있으며,
공통 파일 변경 시 앱별 영향 범위를 검토해야 한다.

## 포트폴리오에 사용할 수 있는 설명

한 줄 요약:

상세 설명 예시:

> 지원 이력 동기화 기능을 준비하면서 웹앱과 익스텐션의 데이터 계약을 함께 수정·검증할 필요가 생겼습니다. 기존 웹앱 저장소를 유지한 채 앱별 경로와 루트 잠금 파일을 구성하고, 익스텐션 이력을 merge 부모로 연결했습니다. 의존성 hoisting에 따른 로컬 폰트 경로 오류와 Vercel 산출물 경로 오류를 수정했으며, 열린 Node 버전 범위도 제한했습니다. 전환 전후 243개 테스트와 앱별 CI·빌드를 확인하고 병합된 dev의 Preview 배포를 완료했습니다. 실제 로그인 수집 검증과 지원 이력 자동 표시는 후속 단계로 분리했습니다.

## 이후 기록을 이어가는 방식

각 단계마다 해당 기능 문서에 다음을 남기고 [문서 인덱스](README.md)에서 연결한다.

- 발생 조건과 관찰 결과: 실제 재현과 잠재 가능성을 구분한다.
- 원인과 선택: 대안, 채택 이유, 비용과 유지해야 할 계약을 기록한다.
- 코드 근거: 이슈·PR·커밋·변경 파일을 연결한다.
- 검증 근거: 실행 환경·명령·결과·실패 사례와 미검증 범위를 남긴다.
- 완료 상태: 구현, dev 통합, Preview, 운영 배포, 스토어 출시를 구분한다.

다음 단계는 [마감일 검증](DEADLINE_VALIDATION.md)이다.
실제 로그인 검증 결과는 사용자가 전달한 결과를 확인한 뒤 추가한다.

## 6단계 후속 사례: 정확한 이력 표시와 DOM 비용 관리

동일 모노레포의 shared 공고 식별 계약을 실제 채용 페이지 표시에도 재사용했다.
수집 스냅샷과 웹앱 기준 캐시를 분리한 상태에서, 원본 공고 textContent를 보존하는 배지와
증분 DOM 처리·가시성 중단·저장소 구독 해제를 구현했다.
TreeWalker가 제거된 하위 트리를 붙잡는 회귀를 재현하고 cursor 정리로 수정했다.
5,000개 링크·20,000개 키 표본의 성능, 반복 생성/제거와 실제 MV3/웹앱 흐름은
[자동 표시 사례 기록](APPLICATION_HISTORY_BADGES.md)에 수치·검증 제한과 함께 남긴다.
