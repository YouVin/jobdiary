# 잡코리아·사람인 지원 이력 자동 표시

구현일: 2026-11-04. 단계별 계획 6단계.
추적: [#117](https://github.com/YouVin/jobdiary/issues/117).
이력의 기준과 동기화 계약은 [5단계 기록](APPLICATION_HISTORY_SYNC.md)을 따른다.

## 결과와 지원 범위

웹앱에서 동기화한 이력과 정확히 같은 사이트·공고 ID인 텍스트 링크에 작은 배지를 표시한다.
현재 지원 범위는 잡코리아와 사람인이다.
배지의 두 문구는 **지원 이력 있음**, **지원취소 이력**이다.
회사명/제목 유사성으로 추정하거나, 일치하지 않는 항목에 미지원 판정을 붙이지 않는다.

| 대상 | 표시 조건·검증 범위 |
| --- | --- |
| 잡코리아 목록·추천 영역 | 허용 호스트의 /Recruit/GI_Read/{ID} 텍스트 링크가 캐시와 일치할 때. 고정 표본 실제 브라우저 검증 |
| 잡코리아 상세 | 현재 URL이 일치하고 비어 있지 않은 h1 후보가 하나인 화면. 공개 원문 구조 확인·표본 브라우저 검증 |
| 사람인 목록 | 허용 공고 경로의 단일 rec_idx가 캐시와 일치할 때. 공개 목록 원문 링크 확인·표본 브라우저 검증 |
| 사람인 상세 | 현재 URL 일치와 단일 h1 조건을 만족할 때. 모든 상세 템플릿의 실사용 검증은 남아 있음 |
| 원티드 | 수집 행의 공고 ID/URL이 아직 없어 자동 표시 범위에서 보류 |
| iframe·Shadow DOM 내부 공고 | 이번 탐색 대상에 포함하지 않음 |

목록은 페이지별 카드 클래스나 경로를 일일이 등록하지 않고 공고 링크의 URL로 식별한다.
새 탭·페이지 로드마다 표시 전용 content script가 실행된다.
화면에 링크가 늦게 생겨도 처리하지만 모든 사이트·템플릿의 지원을 의미하지는 않는다.

공개 구조를 확인한 원문:
[잡코리아 상세](https://www.jobkorea.co.kr/Recruit/GI_Read/50200844),
[사람인 목록](https://www.saramin.co.kr/zf_user/jobs/list/domestic).
2026-11-04 잡코리아 원문에는 빈 로고 h1과 실제 제목 h1이 있어 텍스트가 있는 단일 후보를 사용했다.
사람인 원문에서는 추적 쿼리와 함께 rec_idx가 있는 공고 링크를 확인했다.
로그인된 /User/AI 화면의 현재 DOM은 직접 읽지 못했다. 제공된 화면과 URL을 참고하되 실계정 확인으로 기록하지 않았다.

## 사용 흐름

1. 모노레포에서 웹앱·익스텐션 개발 서버를 실행하고 개발 확장을 새로고침한다.
2. 처음이거나 과거 주소가 비어 있으면 지원현황을 수집한 뒤 **취준일기로 가져오기**를 실행한다.
   같은 지원 ID의 빈 URL은 5단계 규칙에 따라 보완하고 상태·메모는 보존한다.
3. 기존 DB 이력을 갱신할 때는 **취준일기에서 이력 갱신**을 누른다.
   이 동작은 가져오기 신호 없이 웹앱을 열며 지원내역의 새 수집을 실행하지 않는다.
4. 잡코리아 AI 추천/공고 목록이나 사람인 목록을 새로고침하고, 저장된 공고에 배지가 붙는지 확인한다.
5. 팝업의 핵심 연결 상태를 보고 **지원 이력 표시**를 펼쳐 자동 표시 설정·최근 동기화·미식별 건수·이력 갱신을 확인한다.
6. **지원 이력 자동 표시**를 끄면 열려 있는 대상 페이지들의 배지와 감시 작업을 정리한다.
   설정은 브라우저 로컬에 저장하며 다시 켜면 현재 페이지를 검사한다.
7. **수집 내역 초기화**는 복사·가져오기용 수집 정보만 지운다.
   비교 캐시는 별도로 유지하고 웹앱 로그아웃·계정 전환 때 정리한다.

연결된 공고 수는 표시 대상 사이트의 중복 제거한 공고 수다.
지원 건수와 같지 않을 수 있다. 원티드는 현재 표시 대상 수에서 제외한다.
미식별은 URL 부족 등으로 비교할 수 없다는 뜻이며 미지원 사실을 뜻하지 않는다.

개발 실행:

```powershell
Set-Location C:\jobdiary
npm run dev:extension
# 다른 터미널
npm run dev:web
```

Chrome 압축해제 확장은 apps/extension/dist를 사용하며 웹앱은 localhost:3000으로 연다.
페이지 주입 범위가 바뀌면 익스텐션 개발 서버를 먼저 종료·재시작한다.
그 뒤 확장을 다시 로드하고 기존 채용 사이트 탭도 새로고침한다.
실제로 로드할 apps/extension/dist/manifest.json에 historyBadges 등록이 있는지 확인한다.
실제 Store 배포본은 이번 개발 코드와 별도다.

표시 스크립트는 기존 host_permissions 안의 다음 호스트에 주입한다.

- HTTPS (www.)jobkorea.co.kr.
- HTTPS (www.)saramin.co.kr 및 m.saramin.co.kr.

새 host permission이나 API 권한을 추가하지 않았다. 원티드 수집 주입은 기존대로 유지한다.
표시 주입 범위가 수집 가능 경로를 확장하지 않도록 별도 detectHistoryPlatform을 사용한다.
표시 코드에는 수집 요청·사이트 fetch·공고별 네트워크 조회가 없다.

수집 정보, 비교 캐시, 설정의 저장 키를 분리한다.

- jobdiary:collected: 기존 수집 슬롯.
- jobdiary:application-history:v1:{origin}: 웹앱 기준 비교 정보.
- jobdiary:history-display:v1: 자동 표시 설정. 기본값 enabled=true.

개발/운영 origin은 기존 5단계 계약을 따르며 해당 origin 캐시만 읽는다.
비교 캐시의 회사명·메모·토큰을 페이지로 전달하는 경로는 없다.

## DOM과 기존 기능에 미치는 영향

배지용 span을 공고 링크 또는 조건을 만족하는 제목 안에 넣고 닫힌 Shadow DOM으로 문구와 CSS를 구성한다.
같은 문서의 배지들은 가능한 환경에서 하나의 constructed stylesheet를 공유한다.
텍스트는 textContent로 설정하며 페이지에 inline script를 만들지 않는다.

이 선택은 다음 목적을 가진다.

- 부모 링크/제목의 textContent에 배지 문구가 섞이지 않아 기존 파서의 회사명·공고명을 보존한다.
- 사이트의 일반 CSS와 배지 내부 스타일의 충돌을 줄인다.
- 별도 grid/flex 카드 자식을 추가하지 않고 텍스트 링크 안에서 표시한다.
- 링크 href·지원 버튼·키보드 포커스 동작을 유지한다.

양쪽 실제 파서 결과가 배지 삽입 전후 같은지 회귀 테스트로 확인했다.
표본 브라우저 화면에서도 원래 링크 텍스트와 지원 버튼 bounding box가 같았다.
임의의 사이트 CSS까지 레이아웃 불변을 보장한 것은 아니므로 실제 화면 확인은 별도로 유지한다.

배지는 role=note와 이름을 제공하고 포커스를 가로채지 않는다.
표시 자체는 웹페이지 DOM에서 관찰할 수 있다. 닫힌 Shadow DOM이 표시 사실을 비밀로 만드는 보안 경계는 아니다.
원본 캐시·계정 해시는 DOM에 넣지 않는다.

## 성능과 생명주기 선택

- 캐시가 없거나 꺼져 있거나 해당 사이트 이력이 없으면 전체 탐색·MutationObserver를 시작하지 않는다.
- 캐시에서 현재 사이트의 공고 ID → 지원/취소 Map만 만들어 링크별 조회에 사용한다.
- 초기 탐색은 TreeWalker로 나누고 한 번에 최대 200개 요소 또는 약 6ms를 목표로 처리한다.
- 다음 작업은 16ms 뒤에 예약해 긴 순회가 한 작업으로 이어지지 않게 한다.
- 동적 변경은 추가된 영역·href가 바뀐 링크·관련 텍스트만 큐에 넣는다.
- 대기 루트가 100개 이상 쌓이면 하나의 현재 문서 탐색으로 합친다.
- 배지 자체의 삽입·제거는 감시 피드백에서 제외해 자기 자신을 계속 검사하지 않는다.
- 캐시의 공고 상태가 같고 동기화 시각만 바뀌면 전체 탐색 없이 안내 시각만 바꾼다.
- 삭제된 영역의 연결 상태를 확인해 Map과 순회 커서의 DOM 참조를 정리한다.
- 숨겨진 탭은 observer·대기 작업·배지·공고 Map과 저장소 구독을 정리한다. 복귀할 때는 예전 표시를 비우고 캐시를 다시 읽는다.
- 일반 pagehide는 모든 구독·리스너를 정리한다. BFCache 진입은 페이지 이벤트만 유지하고 저장소 구독·공고 Map을 해제하며, 돌아오면 최신 저장소를 읽은 뒤 표시한다.
- 사이트가 배지를 계속 삭제하면 같은 요소/공고의 5초 내 삽입을 3회로 제한한다.
  주기적인 재삽입 타이머를 두지 않는다. 필요하면 설정 재활성화·페이지 갱신으로 다시 검사한다.

정리·캐시 파싱·제목 조회까지 모든 경우가 항상 6ms 이하라는 뜻은 아니다.
위 수치는 탐색 작업의 분할 기준이며 실제 비용은 아래 표본 측정으로 확인했다.

## 발견한 회귀와 수정

초기 TreeWalker가 body를 루트로 순회할 때, 그 안의 큰 목록이 제거되면
body는 연결되어 있어도 currentNode는 분리된 하위 트리를 가리킬 수 있었다.
루트의 isConnected만 확인하면 제거된 목록을 계속 순회하며 붙잡고,
그 뒤에 남은 다른 영역을 놓칠 수 있었다.

2,000개 링크를 한 프레임만 처리한 뒤 제거하는 테스트에서 남은 footer 공고가 표시되지 않는 오류를 재현했다.
제거 노드에 현재 커서가 포함됐는지와 currentNode 연결 여부도 검사하고,
분리된 커서는 해제한 뒤 현재 body에서 탐색을 재개하도록 수정했다.
수정 후 남은 공고를 찾고, 제거된 2,000개 링크를 계속 방문하지 않는 테스트가 통과했다.

브라우저 측정도 보완했다. 일치 항목이 앞쪽에만 있으면 배지 수가 채워져도 전체 순회가 끝나지 않을 수 있다.
따라서 마지막 링크에도 일치 항목을 둬 완료 시점을 구분했다.
DOM 제거 후 예약 정리를 기다리고 GC는 CPU 유휴 측정 구간 밖에서 실행했다.
체크박스 검증도 저장 완료까지 기다려 비동기 저장 상태를 확인한다.

측정 환경은 Windows, Node 22.13.1, Chromium 151.0.7922.34 headless,
Intel Core i5-10500이다. 한 번의 최종 실행 결과이며 다른 기기의 성능 보장은 아니다.

| 표본 | 관찰 결과 |
| --- | --- |
| 공고 링크 5,000개, 비교 키 20,000개, 배지 1,000개 | 마지막 행까지 표시 약 2355ms |
| 위 표본의 추가 JS heap | 약 2.25MiB |
| 위 구간 TaskDuration 증가 | 약 432.86ms |
| 750ms 유휴 구간 | TaskDuration 약 0.15ms 증가, DOM 노드 변화 0 |
| 긴 목록 제거 후 | DOM 노드 10개로 정리 |
| 500개 링크 생성/제거 3회 | 매회 DOM 노드 10개, 첫/마지막 JS heap 차이 약 13.1KiB |
| 표본 링크·지원 버튼 | 링크 textContent·href 보존, 지원 버튼 위치 동일 |
| 배지 표시 자체가 만든 사이트 HTTP | 추가 요청 없음 |

JS heap은 브라우저 전체 RAM이나 네이티브 DOM 메모리와 다르다.
TaskDuration은 표본 페이지와 자동화 작업의 비용도 포함하며 순수 익스텐션 CPU만 분리한 값은 아니다.
유휴 구간에서는 반복 DOM 변화가 없었다. 원래 슬롯·사이트에 저장하는 데이터나 회사 서버 요청은 추가하지 않았다.

3개 탭에서 설정 전파와 복귀 표시를 검증했다.
사용한 headless 환경에서는 탭들이 visible로 보고되어 실제 비활성 탭의 CPU를 측정한 결과로 설명하지 않는다.
최소화 진단에서도 같은 한계를 확인했다. 숨김 중단/복귀 분기는 DOM 테스트로 검증했고,
사용자 Chrome에서 실제 탭 전환은 출시 전 확인 항목으로 남긴다.

## 남은 확인과 포트폴리오 기록

- 실제 로그인한 잡코리아 AI 추천과 사용자 데이터에서 배지·클릭·줄바꿈을 확인한다.
- 사람인의 실제 목록/상세 템플릿과 탭 전환을 확인한다.
- 공고 ID/URL 없는 원티드·과거 기록은 이름으로 추정하지 않는다.
- 웹앱이 닫힌 동안 다른 기기의 변경을 즉시 알 수 없으므로 마지막 동기화 기준을 안내한다.
- 사용자 브라우저 버전, 긴 목록·다중 탭의 장시간 영향은 표본 검증과 구분한다.
- 공개 정책 게시·시행일/스토어 설명·출시 버전과 운영 배포는 7단계에서 확인한다.

포트폴리오에는 정확한 공고 식별·원본 파서 보존·증분 DOM 처리·리소스 정리·성능 측정과
커서 참조 회귀를 재현해 수정한 과정을 근거로 사용할 수 있다.
모든 사이트의 모든 페이지 지원, 브라우저 전체 메모리 개선율, 실계정 전체 흐름 완료로 설명하지 않는다.

## 사용자 피드백 후속: 팝업 축소와 연결 안내 (#119)

2026-11-04 사용자가 실제 팝업 스크롤과 자동 표시 동작의 이해 어려움을 제보했다.
사진에는 수집 슬롯 15건과 비교 가능한 공고 0개·미식별 35건이 함께 보였다.
두 수치는 서로 다른 저장소의 결과다. 수집 슬롯에만 저장된 내역은 웹앱 기준 배지에 사용하지 않는다.
동기화 시각이 있어도 공고 주소가 없거나 지원되지 않는 주소이면 비교 공고는 0개일 수 있다.
실계정 저장소를 읽은 것은 아니므로 재수집/가져오기 미완료·과거 URL 없음·주소 형식 문제 중
구체적인 원인을 사진만으로 확정하지 않는다. 공고가 미지원이라는 뜻도 아니다.

기본 화면의 설명·시각·미식별 건수·이력 갱신을 native details의 연결 정보 안으로 옮겼다.
사이트 배지는 헤더로 모으고 수집 건수는 3열, 복사·수집 초기화는 2열로 배치했다.
0개인 경우 비교할 수 있는 공고가 없다는 상태와 수집→가져오기 안내를 제공한다.
공고의 표시 위치와 정확한 URL 비교 계약은 유지한다.

익스텐션 202개 테스트·타입 검사·운영/개발 빌드와 실제 Chromium MV3 12개 시나리오가 통과했다.
360×600 뷰포트, 수집 15건 표본에서 기본·미식별 35건·미연결 높이는 각각 349px,
연결 정보 펼침은 449px, 미식별 정보 펼침은 485px였다.
각 상태에서 내부 scrollHeight=clientHeight, 문서 높이≤뷰포트 높이를 확인했다.
가짜 HTTP·데이터를 사용하는 재현 검증이며 사용자 실계정의 배지 표시 확인과 구분한다.
재실행은 기존 verify-history-badges-browser.mjs를 사용하며
로컬 release/badge-validation/popup-compact*.png와 browser-report.json에 결과를 보존한다.

사용자가 localhost 가져오기 완료를 알려온 뒤, 공고 주소의 DB 저장은 정상임을 확인했다.
오래된 다른 웹앱 탭의 과거 snapshot 덮어쓰기를 두 탭 브라우저·단위 테스트로 재현해 수정했다.
원인·최소 조회 비용·실계정과 표본 검증의 경계는 [동기화 후속 기록](APPLICATION_HISTORY_SYNC.md#후속-수정-오래된-웹앱-탭의-비교-캐시-덮어쓰기-119)을 따른다.

## 실행 중인 개발 매니페스트 누락: 연결돼도 배지가 없는 경우 (#121)

2026-11-04 사용자가 연결 공고 수는 표시되지만 입사지원 현황에 배지가 없다고 제보했다.
실제로 사용 중인 apps/extension/dist/manifest.json을 읽자 수집 스크립트 3개만 등록돼 있었고
historyBadges의 loader/module 파일은 있어도 content_scripts 등록이 빠져 있었다.
Vite의 표시 모듈 HTTP 응답도 200이므로 파일 존재·모듈 응답만으로 주입을 증명할 수 없었다.

포트 5173의 프로세스가 모노레포의 Vite임을 확인한 뒤 해당 서버만 재시작했다.
직후 생성된 실제 개발 매니페스트에는 기존 수집 3개와 표시 1개의 등록 및 정확한 5개 호스트가 있었다.
이것은 이 세션의 개발 환경 복구이며 모든 CRXJS 환경의 동일한 동작을 단정하는 것은 아니다.
애플리케이션 파서·배지 로직·권한·주입 범위의 추가 변경은 없다.

앞선 정적 빌드 검증은 실행 중인 개발 dist의 등록 상태를 확인하지 못했다.
검증 스크립트에 manifest 사전 검사를 넣어 표시 등록이 없으면 브라우저 실행 전 실패시키고,
DEV_SERVER_ORIGIN으로 실제 Vite 모듈 요청을 허용해 live 개발 확장을 검증하도록 보완했다.
사이트별 추가 HTTP 요청 수 검사에서는 개발 모듈 요청만 분리한다.

재시작 후 사용자가 로드한 것과 같은 apps/extension/dist를 실제 Chromium에 로드해
배지 표시·동적 링크·팝업·설정·긴 목록을 포함한 기존 12개 시나리오가 통과했다.
사이트 HTTP와 비교 이력은 표본이며 사용자 Chrome의 실제 계정 저장소를 읽거나 바꾸지 않았다.
등록이 빠진 매니페스트 표본에서는 사전 검사가 실패하는 것도 확인했다.
이번 변경은 검증 스크립트·문서여서 앱 단위 테스트와 앱 빌드는 다시 실행하지 않았다.

```powershell
# npm run dev:extension이 실행 중인 저장소 루트에서
$env:EXTENSION_PATH = (Resolve-Path apps/extension/dist).Path
$env:DEV_SERVER_ORIGIN = 'http://localhost:5173'
node apps/extension/scripts/verify-history-badges-browser.mjs
```

BROWSER_EXECUTABLE·PLAYWRIGHT_MODULE이 필요한 환경은 기존 브라우저 검증 문서를 따른다.
기본 실행은 종전의 별도 정적 개발 빌드를 사용하며 DEV_SERVER_ORIGIN은 live 검증 때만 지정한다.
로컬 live-dev.log, dev-restart.*.log, missing-manifest.log와 browser-report.json에 근거를 보존한다.

사용자 Chrome은 생성된 매니페스트를 다시 읽어야 하므로 chrome://extensions에서 취준일기를
새로고침한 뒤 잡코리아 페이지도 새로고침한다. 이 복구에 지원내역 재수집·웹앱 재가져오기는 필요하지 않다.
사용자 실계정 화면의 확인 결과는 표본 Chrome 통과와 별도로 기록한다.

## 사용자 실사용 확인과 초기 팝업 복원 (#123)
