# 모노레포 마감일 수집·전달 검증

검증일: 2026-11-04. 단계: [진행 계획의 4단계](IMPLEMENTATION_ROADMAP.md).
추적 이슈: [#113](https://github.com/YouVin/jobdiary/issues/113).
구현 기준: [익스텐션 DEADLINES](../apps/extension/docs/DEADLINES.md),
[연동 계약](../apps/extension/docs/INTEGRATION.md), [웹앱 마감일 규칙](DEADLINE.md).

## 현재 결론

고정 표본을 사용한 실제 Chromium MV3 검증 8개가 통과했다.
사용자 Chrome의 잡코리아 수집·팝업에서 지원 10건 수집과 마감일 8건 확인을 관찰했다.
사람인 모바일 날짜 보충·원티드 실제 탈락 수집·웹앱 UI/DB 저장은 미검증이다.
사용자가 체크리스트를 따라 직접 확인 중이며 세부 결과는 아래 실사용 기록에 남긴다.
이 문서는 4단계 완료 또는 출시 가능 판정을 의미하지 않는다.

이번 변경은 검증 스크립트와 기록이다. 앱 소스·권한·저장 형식·외부 메시지는 변경하지 않았다.

## 실사용 확인 기록 — 2026-11-04

근거는 사용자가 전달한 팝업 화면과 사용 결과다. 브라우저 버전·실제 날짜 값·웹앱 저장 결과는
전달받지 않았으며, 화면 밖의 결과를 성공으로 추정하지 않는다.

| 항목 | 관찰 결과 | 판정 범위 |
| --- | --- | --- |
| 잡코리아 | 사용자가 정상 동작 확인. 팝업에 10건 수집·마감일 8건 확인 표시 | 실제 수집과 팝업 날짜 확인 건수 검증 |
| 나머지 잡코리아 2건 | 날짜 미확인 또는 날짜 없음 안내 | 정확한 원인은 확인하지 않음. 전체 지원 10건과 구분 |

| 웹앱 | 신규 가져오기·날짜 저장 결과 미제공 | UI/DB 검증 대기 |

원티드의 현재 코드를 확인했다. 상태 텍스트를 파싱하고 공통 어댑터가
불합격/탈락을 `rejected`로 변환한다. 마감일이 없어도 신규 가져오기에서 탈락 상태를
사용할 수 있다. 기존 웹앱 지원은 재수집으로 갱신하지 않으므로, 기존 지원완료 카드가
새 수집 결과의 탈락으로 자동 변경되는 기능은 현재 없다. 이 구분을 사용자에게 안내한다.

사람인은 PC에 날짜가 없다고 임의 추정하지 않는다. 현재 모바일 보충은 선택적이며,
이 대화만으로 제거·지원 중단을 확정하지 않는다. 날짜를 얻지 못하면 생략하고 PC 내역을
유지하는 기존 경계를 따른다.

개발 환경 확인 중 CRXJS DEV MODE의 localhost:5173 연결 안내가 나타났다. 이후 기존
개발 서버 응답과 생성 파일의 5173 참조를 확인하고 확장 재로드를 안내했다. 사용자는
이후 정상 팝업을 제공했다. 최초 연결 안내의 정확한 발생 원인은 확정하지 않았다.

## 자동 검증 재실행

저장소 루트에서 실행한다. 기존 전체 테스트·빌드는 이전 단계와 CI에서 통과했으며,
이 검증은 실제 확장 실행 경계를 추가로 확인한다.

```powershell
Set-Location C:\jobdiary
npm.cmd exec --workspace=jobdiary-extension -- vite build --mode development --outDir ../../release/deadline-validation/extension
node apps/extension/scripts/verify-deadline-browser.mjs
```

기존 선택적 브라우저 도구인 `apps/web/node_modules/.release-tools`의 Playwright를 사용한다.
런타임 의존성이나 필수 CI 단계로 추가하지 않았다. 도구가 없는 새 작업 환경에서는
별도 도구 폴더에 Playwright와 Chromium을 준비해야 한다.

환경에 따라 아래 값을 지정할 수 있다.

- `PLAYWRIGHT_MODULE`: 설치한 Playwright의 `index.mjs` 절대 경로.
- `BROWSER_EXECUTABLE`: 확장 로드를 지원하는 Chromium 실행 파일 절대 경로.
- `EXTENSION_PATH`: 위와 같은 development 정적 빌드 출력 폴더.

이번에는 기존 Playwright가 기대하는 기본 브라우저 캐시 버전이 없어서 이미 설치된
Chromium의 실행 파일을 `BROWSER_EXECUTABLE`로 지정했다.
브라우저 설치 버전은 실행 보고서에 기록된다.
브라우저·도구 버전이 다른 환경에서 동일 결과를 보장하지 않는다.

정적 검증 빌드 경로와 실제 사용자가 개발 서버로 로드할 `apps/extension/dist`는 다르다.
스토어용 빌드는 `npm run build:extension`이지만 개발 ID·localhost 확인에는 사용하지 않는다.
검증 빌드가 만든 동일 버전 ZIP도 스토어에 제출하지 않는다.

## 직접 확인: 2. 사람인 수집

1. PC 사람인 지원현황 `https://www.saramin.co.kr/zf_user/persons/apply-status-list`에서 로그인과 목록 표시를 확인한다.
2. 가능하면 같은 Chrome 프로필에서 모바일
   `https://m.saramin.co.kr/apply/state?local_code=&appmode=need_login`도 열어
   로그인 화면인지 지원 카드가 보이는지 확인한다.
3. PC 지원현황으로 돌아와 새로고침하고 익스텐션의 **지원내역 수집하기**를 누른다.
4. 수집 건수와 **마감일 N건 확인** 또는 조회 실패 안내를 기록한다.
5. 모바일 첫 응답에 PC와 같은 지원이 있고 연도 포함 날짜가 명시된 경우 날짜 보충을 확인한다.

기대 결과와 해석:

- [ ] PC 지원은 정상 저장되고 기존 회사·포지션·상태·지원일이 유지된다.
- [ ] 명시된 날짜를 찾으면 일치하는 지원에만 날짜가 붙는다.
- [ ] 모바일 조회가 실패해도 지원내역은 저장되며 팝업에 그 사실이 표시된다.
- [ ] 0건은 응답 오류와 구분한다. 모바일 첫 응답에 일치하는 두 ID와 명시 날짜가 없으면 정상적으로 0건일 수 있다.

모바일은 첫 응답만 확인한다. 과거 표본 날짜가 현재도 표시된다고 가정하지 않는다.
로그인 성공 사례나 명시 날짜가 없으면 해당 검증을 `미검증: 표본 없음`으로 남긴다.

## 직접 확인: 3. 잡코리아·원티드와 재수집

1. 잡코리아에서 로그인 후 실제 **입사지원현황**으로 이동한다.
   `/User/AI` 추천공고 목록은 이번 지원내역 수집 검증 대상이 아니다.
2. 지원현황을 새로고침하고 수집한다. 날짜가 있는 지원과 상시채용 지원이 있으면 각각 확인한다.
3. 원티드 지원현황에서도 수집하고 기존 건수·상태가 유지되는지 확인한다.
4. 사이트별 수집 뒤 다른 사이트의 저장 건수가 유지되는지 확인한다.
5. 같은 사이트를 다시 수집하고 해당 사이트 슬롯이 교체되며 중복 누적되지 않는지 확인한다.

- [ ] 잡코리아는 PC 목록의 연도 없는 `(~MM/DD)`만으로 날짜를 추정하지 않는다.
- [ ] 연결된 공개 공고의 공고 ID·메타 설명·구조화 날짜가 일치할 때만 보충한다.
- [ ] 상시채용은 구조화 날짜가 있어도 마감일로 전달하지 않는다.
- [ ] 공고 조회 실패 시 지원은 남고 조회 실패 안내가 표시된다. 실제 실패가 없으면 표본 검증만 통과로 남긴다.
- [ ] 원티드는 마감일이 없는 상태로 기존 수집 기능이 동작한다.

잡코리아는 최대 10개 공고·동시 2건·요청당 4초 제한이 있다.
그 밖의 지원이 날짜 미확인인 것을 수집 누락으로 오해하지 않는다.
원티드는 공고 ID/URL·마감일 출처가 없어 이번에 보충하지 않는다.

## 직접 확인: 4. 웹앱 신규 가져오기와 기존 항목

실제 본인 웹앱 계정에 지원을 추가하는 동작이다. 최초 확인은 본인이 추가해도 되는
지원으로 진행하고 기존 카드를 삭제해 신규 항목을 만들지는 않는다.

1. 날짜가 확인된 지원 중 웹앱에 아직 없는 항목을 선택한다.
2. 익스텐션의 웹앱 열기를 사용하거나 localhost 웹앱의 **익스텐션에서 가져오기**를 실행한다.
3. 로그인 후 새 지원의 마감일을 카드·상세 또는 수정 화면에서 확인한다.
4. 웹앱을 새로고침해 저장된 날짜가 유지되는지 확인한다.
5. 같은 데이터를 다시 가져와 기존 항목이 건너뛰어지는지 확인한다.
6. 이미 수동 변경한 상태·메모가 있는 항목은 재수집 후에도 그대로인지 확인한다.

- [ ] 신규 지원의 날짜가 `YYYY-MM-DD` 기준으로 일치하고 새로고침 후에도 남는다.
- [ ] 마감일 없는 지원도 정상적으로 추가된다.
- [ ] 반복 가져오기는 중복을 만들지 않는다.
- [ ] 기존 카드의 마감일을 자동 보충하지 않는 현재 계약을 확인한다.
- [ ] 기존 수동 상태·메모·일기가 덮어써지지 않는다.
- [ ] 과거 마감일·지원완료·자동 분류 대상이면 웹앱 규칙에 따른 상태 변경과 근거 표시를 확인한다.
  이것은 기업의 공식 불합격 통보가 아니다. 수동 상태는 자동 분류 대상에서 제외한다.

Preview 도메인은 확장 외부 통신 허용 대상이 아니므로 이번에는 localhost를 사용한다.
모노레포 dev를 운영 배포하기 전에 운영 웹앱의 결과만으로 새 코드 검증을 대신하지 않는다.

## 결과를 전달할 간단한 양식

공유할 때 회사명·지원 ID·이력서 링크·쿠키·토큰이나 전체 HTML은 필요하지 않다.
아래처럼 건수·문구·성공/실패만 전달하면 된다.

```text
Chrome 버전 / 개발 확장 ID:
사람인: 수집 __건 / 마감일 __건 / 안내 문구:
모바일: 로그인 화면 또는 지원 목록 / 연도 포함 날짜 표본 있음·없음
잡코리아: 수집 __건 / 마감일 __건 / 안내 문구:
원티드: 수집 __건 / 기존 수집 이상 있음·없음
재수집: 중복 누적 없음·있음 / 다른 사이트 건수 유지 여부
웹앱 신규: 마감일 일치·불일치·표본 없음 / 새로고침 후 유지 여부
웹앱 기존: 중복 없음·있음 / 수동 상태·메모 유지 여부
막힌 단계와 오류 문구:
```

결과는 확인 날짜·환경·표본 유무와 함께 이 문서에 추가한다.
없는 표본·미실행·실패를 성공으로 바꾸지 않는다.
전체 4단계의 판정은 자동 검증, 실제 로그인 결과, 남은 제한을 함께 보고 기록한다.
