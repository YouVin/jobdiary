설계·실측 전체는 [POSTING_ANALYSIS](POSTING_ANALYSIS.md), 결정은 [결정 기록 001~003](decisions/README.md)에 있다. 비용은 Claude Haiku 5.5 기준이고, 원화는 1달러 약 1,400원으로 계산했다.

## 1. 공고 1건 정리 비용·시간 (#226)

- **문제:** 지원 건마다 AI를 부르면 비용과 대기 시간이 쌓인다. 처음 만든 방식(baseline)은 회사 소개를 3~5문장으로 쓰고, 강점을 찾을 수 있는 만큼 찾고, 생각 깊이도 모델 기본값이었다.
- **측정:** 가상 프론트엔드 공고 1개(1,230자) + 실제 회사 자료 + 홈페이지 요약 850자로 baseline과 lean을 1번씩 돌렸다(`scripts/eval-posting-analysis.mjs`).
- **수정(lean):**
  - 생각 깊이를 `low`로 낮췄다.
  - 복리후생·지원 방법 같은 칸은 공고에서 뺐다. 인용 검사를 위해 줄 내용은 고치지 않고 칸 단위로만 뺐다.
  - 회사 소개는 한 문장, 강점은 최대 5개, 인용은 100자 이내로 줄였다.
- **결과:**

  | | baseline | lean |
  |---|---|---|
  | 입력 / 출력 토큰 | 3,520 / 3,045 (생각 1,644) | 3,161 / 809 (생각 0) |
  | 1건 비용 | $0.0019 (약 2.6원) | **$0.0007 (약 1원)** |
  | 응답 시간 | 12.8초 | **4.6초** |
  | 인용 정확도 | 100% (8/8) | 100% (5/5) |

- **교훈:** 절감의 대부분은 생각 토큰이 0이 된 데서 왔다. 프롬프트 캐싱은 요청이 1~2시간에 1번꼴이라 5분 캐시가 대부분 만료돼 오히려 1.25배를 내므로 쓰지 않았다.
- **남은 것:** 결과 형식(JSON 스키마)이 입력을 약 820~850토큰 차지한다. 무료 토큰 세기 결과와 실제 청구 토큰을 비교해 잰 값이다.

## 2. 이미지로 된 공고 (#232)

- **문제:** 채용 공고 본문이 대부분 이미지라 글 붙여넣기로는 쓸 수 없었다.
- **원인:** Claude는 긴 변이 약 1,568px를 넘는 이미지를 줄여서 읽어, 긴 공고를 한 장으로 보내면 글자가 뭉개진다.
- **수정:**
  - 브라우저에서 가로 1,000px 이하로 줄이고, 세로 1,400px씩 60px 겹쳐 잘라 JPEG 0.9로 보낸다.
  - AI가 이미지의 글을 먼저 그대로 옮겨 적게(`transcript`) 하고, 그 글로 분석하고 인용을 검사한다.
- **결과(실제 호출 1번):**
  - 860×2,246px 공고 이미지가 2조각(390KB)이 됐다.
  - 13.0초, 입력 4,744·출력 2,128토큰, **$0.00154(약 2.2원)**.
  - 옮겨 적기는 **44줄 중 44줄**, 글자 수 891 = 891로 원문과 같았다. 인용 검사 5/5.

## 3. 이미지 토큰 예측 (#232)

- **문제:** 이미지 비용을 미리 알아야 조각 수 상한(12조각)과 하루 한도를 정할 수 있다.
- **방법:** 28×28픽셀당 1토큰으로 계산하고, 무료 토큰 세기 API로 실제 값을 쟀다.
- **결과:** 계산 **2,573토큰** vs 실제 약 **2,580토큰**(0.3% 차이). 이 계산식을 자르기 계획 테스트에 넣었다.

## 4. 결과가 애매하고 정보가 많음 (#235)

- **문제:** 실제로 써 보니, 강점 "이유"가 공고 인용을 바꿔 말하는 수준이었다. 읽은 글 전체·기술 목록·예상 질문까지 보여 줘서 정보가 너무 많았다(사용자 피드백).
- **수정:**
  - 결과를 세 덩어리로 바꿨다.
    1. **이 회사는:** 하는 일, 대표 서비스, 대표 사이트.
    2. **원하는 강점:** 강점마다 "이런 경험을 넣으면 좋아요"를 붙이고, 공고 근거는 접어 둔다.
    3. **근무 조건:** 네이버 지도 링크, 근무일, 근무 시간.
  - 강점은 최대 5개에서 4개로 줄였다.
  - 대표 사이트는 공고에 실제로 적힌 주소만 남긴다.
- **결과(실제 호출 1번):** 입력 3,711·출력 886토큰, 약 1원, 5.6초, 인용 4/4.

## 5. 실제 캡처에서 강점이 빔 (#237)

- **문제:** 어두운 배경·작은 글씨의 긴 공고 페이지 전체를 한 장으로 캡처했더니 강점이 **0개**였다("인재상 근거를 찾지 못했어요").
- **원인:**
  - 지시문이 "인재상 문장이 없으면 강점을 비운다"를 강조했다. 인재상 칸 없이 업무·자격에 강점이 녹아 있는 공고에서 비었다.
  - 인용 검사가 기호·공백 차이에도 강점을 버렸다. 몇 개를 버렸는지 기록이 없어 확인할 수 없었다.
  - 페이지 전체를 줄인 캡처는 글씨가 작았다.
- **수정:**
  - 지시문: 인재상 칸이 없어도 주요 업무·자격 요건에서 강점을 찾고, 업무·자격 내용이 있으면 최소 2개를 낸다.
  - 인용 검사: 글자·숫자만 비교한다. 지어낸 문장은 계속 막는다.
  - 진단 기록: 읽은 글 길이, AI가 낸 강점 수, 남긴 강점 수를 숫자로만 저장한다.
  - 가로 700px 미만 이미지에는 "확대해 캡처" 안내를 띄운다.
- **한계:** 같은 캡처로 수정 후 실측은 하지 않았다. 캡처 품질에 결과가 달려 있다는 문제 자체는 6번(공고 페이지 읽기)으로 풀었다.

## 6. 근무지가 "서울"만 나옴 (#237 → #238)

- **문제:** 근무지가 "서울"처럼 시·도까지만 나왔다.
- **원인:** 상세 근무지는 공고 본문이 아니라 위쪽 요약 칸에 있다. 사용자가 본문만 캡처하면 AI가 알 수 없다.
- **수정:** 지원에 저장된 공고 주소를 익스텐션이 읽는다.
  - 잡코리아는 JSON-LD, 원티드는 `__NEXT_DATA__`, 사람인은 "근무지 :" 줄에서 근무지를 읽는다.
  - 서버는 근무지·근무 일정에 **AI 값보다 페이지 값을 우선**한다.
  - 원본 이미지(예: 860×5,017px)도 사용자 캡처보다 선명하다.
- **결과:** 실제 공고 **4개 중 4개**(잡코리아 2·사람인 1·원티드 1)가 도로명 주소까지 나왔다. 예: "서울 강남구 도산대로56길 5 (청담동) 지하1층,1층".
- **뒤이은 결정(#242):** 결과가 만족스러워 캡처·글 붙여넣기 입력을 없애고 "공고 페이지에서 가져오기" 하나만 남겼다. 회사 정보는 서류 통과 단계부터 만들 수 있게 했다.

## 7. 잡코리아 본문 이미지를 브라우저가 못 받음 (#238)

- **문제:** 사람인 이미지 서버(`*.saraminimage.co.kr`)는 다른 사이트의 읽기(CORS)를 허용한다. 잡코리아(`file*.jobkorea.co.kr`)는 허용하지 않아 브라우저가 이미지를 받지 못했다.
- **수정:** Edge Function `posting-image`가 대신 받는다. 아무 주소나 받으면 서버를 통해 내부망을 찌르는 공격(SSRF)에 쓰일 수 있어 다음 조건을 모두 건다.
  - 로그인 필요
  - 허용 목록(공유 계약 `isPostingImageUrl`과 같은지 테스트로 비교)
  - https만, 리다이렉트 거절
  - 이미지 형식만, 10MB까지
- **결과:** 검증에서 서버 대신 받기는 허용 주소 1개에 1번만 일어났다. 받은 이미지는 저장하지 않는다. 익스텐션 권한은 바꾸지 않았다(출시 패키지 검사).

## 8. 서버가 보낸 이미지가 깨짐 (#238)

- **문제:** `supabase.functions.invoke`로 `posting-image`를 부르면 이미지가 깨졌다.
- **원인:** `functions.invoke`가 `image/*` 응답을 글자로 읽는다.
- **수정:** 함수 주소를 사용자 토큰과 함께 직접 `fetch`해 Blob으로 받는다. 서버(Deno) 쪽에서는 `Uint8Array`를 응답 본문으로 넘기면 타입 오류가 나서 Blob으로 감쌌다.

## 9. 로컬에서 "최신 버전으로 업데이트" 안내가 뜸 (#238)

- **문제:** 새 익스텐션을 설치했는데(팝업도 새 디자인) 웹앱이 "익스텐션을 최신 버전으로 업데이트하면…"이라고 안내했다.
- **원인:**
  - `npm run build`는 출시용(production) 빌드라 고정 ID 키가 없고, `localhost:3000`의 요청을 받지 않는다.
  - 로컬 웹앱은 개발용 고정 ID(`dckf…`)로 요청을 보내므로 받는 익스텐션이 없었다.
  - 웹앱은 응답이 없으면 "이전 버전"으로 판단한다.
- **수정:** 로컬 확인은 `vite build --mode development`로 빌드한다. 빌드한 `manifest.json`에 `key`와 `localhost:3000`이 들어간 것을 확인했다.
- **남은 것:** "연결 안 됨"과 "예전 버전"을 같은 문구로 보여 준다. 구분할지는 정하지 않았다.

## 10. 사이트가 다르면 같은 공고도 중복으로 안 잡힘 (#220)

- **문제:** 같은 회사·같은 공고에 사람인과 잡코리아로 지원했는데 "중복"에 잡히지 않았다. 예: (주)루트랩스(예시)는 사람인에서 "프론트엔드", 잡코리아에서 "[IT/통신] ROOT LA…"로 들어왔다.
- **원인:**
  - 회사명과 공고명이 글자 그대로 같을 때만 묶었다.
  - 사이트마다 공고명 칸이 다르다. 사람인은 모집 부문을 쓰고, 잡코리아는 공고 제목 전체를 쓴다.
- **수정:**
  - 회사명: (주)·주식회사 같은 법인 표기와 공백·기호를 빼고 비교한다.
  - 공고명: 말머리와 흔한 말(채용·신입 등)을 빼고, 한쪽 핵심 단어가 다른 쪽에 모두 들어 있으면 같은 공고로 본다.
  - 같은 회사의 다른 직무는 중복으로 보지 않는다.
- **결과:** 예시 2,000건(같은 공고를 다른 표기로 섞음)에서 비교했다.

  | | 이전 | 첫 구현 | 최종 |
  |---|---|---|---|
  | 시간 | 2.20ms | 15.7ms | 2.79ms |
  | 묶음 | 0개 | — | 267개 |

  첫 구현은 쌍마다 이름을 정리하고 `localeCompare`를 썼다. 최종은 회사별로 나눠 같은 회사 안에서만 비교하고, 정리 결과를 기억하고, 날짜 정렬은 글자 비교로 바꿨다.

## 11. 결과 형식(JSON 스키마)이 입력 토큰의 25% (#260)

- **문제:** 회사 정보 1건의 입력이 3,828토큰인데, 공고 내용(1,411)보다 지시문(1,460)과 결과 형식(957)이 더 많았다. 결과 형식은 응답 모양을 정하는 JSON 스키마로, 보내는 글이 아니라서 눈에 띄지 않았다.
- **잰 방법:** 무료 토큰 세기 API(`count_tokens`)만 썼다. 모델을 실행하지 않아 비용이 없고, 같은 입력이면 같은 숫자가 나온다. 부분은 차이로 구했다(형식 = 전체 − 형식 없이, 지시문 = 지시문 + 한 글자 메시지). 재현: `apps/web`에서 `node scripts/count-analysis-tokens.mjs`. 공고는 측정용 가상 공고 1건(비주얼캠프, 회사 자료·홈페이지 글 포함)이다.
- **원인:**
  - 강점 이름 12개가 **두 번** 들어갔다. 지시문의 "이름: 설명" 목록과 스키마의 `enum`(허용 값 목록)이다. 스키마는 문법 기호와 함께 들어가 한글 이름 12개만으로 약 300토큰이 됐다.
  - `hasTalentStatement`(인재상 있음 여부)는 `strengths`가 비었는지로 알 수 있는 값인데 칸과 규칙 문장을 따로 뒀다. 화면에서도 쓰지 않았다.
- **고른 방법:** 줄일 후보를 품질 위험 순으로 나눠 먼저 무료로 쟀다.

  | 후보 | 입력 토큰 | 품질 위험 |
  |---|---|---|
  | 지금 | 3,289 | — |
  | ① 스키마의 강점 `enum` 빼기 | 2,988 (−9.2%) | 낮음: 목록이 지시문에 그대로 있고, 서버가 검사 |
  | ①+ `hasTalentStatement` 빼기 | 2,950 (−10.3%) | 낮음: 같은 뜻을 `strengths`로 판단 |
  | ② 지시문 강점 목록을 설명 없이 한 줄로 | 2,693 (−18.1%) | 있음: 설명이 강점 고르기 기준이라 실제 결과 비교 필요(유료) |
  | ③ 지시문 목록 빼고 `enum`만 | 2,910 (−11.5%) | 있음: 설명이 사라짐 |

  (이 표는 회사 자료·홈페이지 글 없이 공고 글만 넣은 사전 측정이다. 아래 결과는 자료를 포함한 실제 요청 모양.)

  비용 없이 바로 할 수 있고 품질이 그대로인 ①만 했다. ②는 실제 공고로 결과를 비교해야 해서(건당 1~2원) 따로 정한다.
- **수정:**
  - 스키마에서 강점 `enum`과 `hasTalentStatement`를 뺐다. 지시문의 강점 목록("이름: 설명")은 그대로 둔다.
  - 대신 서버가 `keepKnownStrengths`로 강점 이름을 검사한다. 띄어쓰기만 다르면("소통능력") 목록 이름으로 고치고, 목록에 없는 이름은 버린다. 버린 수는 진단(`strengthsUnknownLabel`)과 로그에 숫자로 남겨, `enum`을 뺀 뒤 목록 밖 이름이 실제로 나오는지 볼 수 있게 했다.
  - 지시문 버전을 `2026-11-25.5`로 올렸다. 예전 형식으로 저장된 결과는 그대로 읽는다(화면은 `hasTalentStatement`를 쓰지 않음).
- **결과:**

  | | 전체 입력 | 결과 형식 | 지시문 | 공고·자료 |
  |---|---|---|---|---|
  | 글 공고 전 | 3,828 | 957 (25.0%) | 1,460 | 1,411 |
  | 글 공고 후 | **3,473 (−9.3%)** | **618 (−35.4%)** | 1,444 | 1,411 |
  | 이미지 공고 전 | 4,158 | 983 | 1,764 | 1,411 |
  | 이미지 공고 후 | **3,803 (−8.5%)** | **644 (−34.5%)** | 1,748 | 1,411 |

  (이미지 공고는 이미지 자체 토큰을 빼고 형식·지시문만 비교했다.)
- **금액으로는:** Haiku 5.5 입력은 100만 토큰당 $0.10이라 355토큰은 건당 약 0.05원이다. 하루 5번 한도에서는 작은 금액이고, 이 작업의 의미는 "형식도 입력 토큰"이라는 점을 재서 확인한 데 있다. 공고가 짧을수록 비중이 크다(짧은 예시 공고: 형식이 입력의 37%).
- **검토하고 보류한 것 (지시문 캐시):** Haiku 5.5는 512토큰부터 캐시되므로 지시문(약 1,450토큰)은 캐시할 수 있다. 다만 캐시는 5분 안에 같은 지시문으로 다시 요청이 와야 이득이다. 캐시에 쓸 때는 그 부분이 1.25배, 읽을 때는 0.1배라서, 대략 요청 4~5번 중 1번 이상이 5분 안에 이어져야 본전이다. 지금 사용량(하루 몇 건)에서는 쓰기 비용만 늘어 보류했다. 홍보 뒤 사용량 지표(#256)에서 회사 정보 생성이 몰리는 시간이 보이면 다시 계산한다.
- **검증:** 웹 테스트 180개 통과. 새 테스트: 스키마에 `enum`·`hasTalentStatement` 없음, 지시문에 강점 12개가 모두 있음, 이름 고치기·버리기, 서버가 목록 밖 이름을 버리고 진단에 남김. 실제 AI 결과로는 아직 확인하지 않았다(운영 반영 뒤 진단의 `strengthsUnknownLabel`로 본다).

## 12. 전형 절차를 가져올 때 모든 지원에 읽기 (#295)

- **문제:** 지원마다 공고의 전형 절차("서류 → 코딩테스트 → 1차 면접 → 최종 합격", 회사마다 이름이 다름)로 단계를 만들려면 가져온 지원 전부를 읽어야 한다. 회사 정보 AI(강점·근무 조건까지, 1건 약 1~2.2원)에 붙이면 지원 수만큼 비용이 든다.
- **수정:**
  - 공고 글에 절차가 적혀 있으면 규칙으로 읽는다(비용 0). 받은 공고 7개 중 4개가 글이었다.
  - 이미지뿐이거나 규칙으로 못 찾은 공고만 **절차 전용** 요청을 쓴다. 지시문 5줄·결과 형식(이름·종류) 작게, 생각 깊이 low, 출력 1,024토큰 한도.
  - 같은 공고는 서버가 결과를 재사용하고(공고 지문), 한 화면 안에서도 같은 공고 주소는 한 번만 읽는다. 사용자별 하루 60번 한도.
- **실측(실제 호출 7번, 공고 화면 이미지 1장씩, `scripts/eval-hiring-process.mjs --run`):**

  | 공고 | 입력 / 출력 토큰 | 비용 | 시간 | 결과 |
  |---|---|---|---|---|
  | 7건 범위 | 1,140~2,523 / 56~132 | 0.25~0.41원 | 1.2~3.0초 | 7건 모두 공고 이름 그대로, 종류(서류·테스트·면접·최종) 맞음 |
  | 합계 | | **2.18원** | | |

  예: "서류 접수 → 사전 설문조사(테스트) → 1차 인터뷰 → 과제 전형(테스트) → 2차 인터뷰 → 처우 협의와 채용(최종)".
- **남은 것:** 실제 공고 이미지는 조각 여러 장(최대 8장)이라 1건 입력이 더 클 수 있다(조각 1장 약 2,580토큰 → 8장이면 약 2.9원). 운영에서 `posting_processes.cost_usd`로 실제 평균을 본다.

## 13. 이미지 공고에서 설명 없는 강점 (#322)

- **문제:** 이미지 공고로 만든 회사 정보에서 강점 카드가 강점 이름과 접힌 "공고 근거 보기"만 보였다. 원하는 모습(`wants`)과 넣으면 좋은 경험(`experiences`)이 비어 있었다(사용자 발견).
- **잰 방법:** 운영 `posting_analyses`를 읽기 전용으로 집계했다. 내용은 보지 않고 숫자(강점 수, 빈 칸 수, 옮겨 적은 글 길이, 출력 토큰)만 봤다(2026-11-28).

  | 지시문 버전 | 공고 | 결과 | 강점 | 설명 둘 다 빔 |
  |---|---|---|---|---|
  | 2026-11-25.4 | 이미지 | 1 | 4 | 0 |
  | 2026-11-25.5 | 글 | 1 | 4 | 0 |
  | 2026-11-25.5 | 이미지 | 3 | 5 | **3** |

  2026-11-25.5 이미지 공고 3건을 한 건씩 보면, 설명이 빈 2건은 강점이 **전부** 비었고 옮겨 적은 글이 길었다(1,963자·1,672자). 설명이 채워진 1건은 글이 짧았다(448자). 출력은 셋 다 약 2,000토큰으로 상한(`max_tokens`)에는 닿지 않았다.
- **원인:**
  - 결과 형식은 두 칸을 요구하지만 빈 글·빈 목록도 통과한다. 서버는 강점 이름(#260)과 인용(#237)만 검사했다.
  - 이미지 공고는 글을 먼저 전부 옮겨 적은 뒤 분석한다. 글이 길 때 뒤쪽 칸을 비우는 것으로 보인다(3건이라 추정).
  - 화면은 설명이 비어도 근거를 접어 두어 빈 카드처럼 보였다.
- **수정:**
  - 서버: 원하는 모습과 경험이 모두 빈 강점은 버린다(`keepExplainedStrengths`). 버린 수는 진단(`strengthsUnexplained`)과 로그에 숫자로 남긴다. 모두 버려지면 "인재상 근거를 찾지 못했어요"가 보인다.
  - 화면: 이미 저장된 결과에서 설명이 빈 강점은 근거를 펼쳐 보여 준다.
- **남은 것:** 지시문을 고쳐 이미지 공고에서도 두 칸을 채우게 하는 것은 실제 호출로 확인해야 해서(건당 약 1원) 따로 정한다. 운영 반영 뒤 `strengthsUnexplained`가 계속 나오면 그때 한다.
